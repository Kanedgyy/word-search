# Архитектура приложения "Соревновательный филворд"

## 1. Общее описание

Приложение представляет собой клиент-серверное веб-приложение для игры в филворд (поиск слов в таблице букв) с поддержкой многопользовательского режима.

## 2. Архитектурные решения

### 2.1 Клиент-серверная архитектура

```
┌─────────────────┐         HTTP/WebSocket         ┌─────────────────┐
│                 │ ◄────────────────────────────► │                 │
│   Клиент        │                                │   Сервер        │
│   (Next.js)     │         tRPC API               │   (Next.js API) │
│                 │ ◄────────────────────────────► │                 │
└─────────────────┘                                └─────────────────┘
                                                          │
                                                          ▼
                                                   ┌─────────────┐
                                                   │  PostgreSQL  │
                                                   │   (Drizzle)  │
                                                   └─────────────┘
```

### 2.2 Выбор технологий

#### TypeScript
**Обоснование:** Статическая типизация позволяет обнаруживать ошибки на этапе компиляции, а не в runtime. Автодополнение в IDE ускоряет разработку.

**Сравнение с альтернативами:**
- JavaScript — отсутствие типизации, больше ошибок в runtime
- Flow — меньшее сообщество, хуже поддержка в IDE

#### Next.js 16
**Обоснование:** Современный React-фреймворк с App Router, серверными компонентами и встроенной оптимизацией.

**Сравнение с альтернативами:**
- Create React App — устаревший, нет SSR
- Remix — меньше экосистема, сложнее деплой
- Vue/Nuxt — другой стек, меньше библиотек для React

#### tRPC
**Обоснование:** Полная типизация API между клиентом и сервером. Не нужно писать Swagger/OpenAPI спецификации.

**Сравнение с альтернативами:**
- REST — нужно писать документацию, нет типизации
- GraphQL — сложнее, нужен codegen, избыточен для простого API
- gRPC — не работает в браузере напрямую

#### Drizzle ORM
**Обоснование:** Лёгкий, быстрый ORM с полной типизацией. Прямой SQL-подход без магии.

**Сравнение с альтернативами:**
- Prisma — тяжелее, медленнее, требует генерации клиента
- TypeORM — больше магии, сложнее в использовании
- Knex — query builder, но без типизации схемы

#### PostgreSQL
**Обоснование:** Надёжная реляционная БД с поддержкой JSONB и массивов.

**Сравнение с альтернативами:**
- MongoDB — нет ACID, сложнее агрегации
- MySQL — меньше возможностей для сложных типов
- SQLite — не подходит для многопользовательского режима

#### Tailwind CSS
**Обоснование:** Утилитарные классы позволяют быстро создавать адаптивные интерфейсы.

**Сравнение с альтернативами:**
- CSS Modules — больше кода, сложнее поддерживать
- Styled Components — runtime overhead, сложнее с SSR
- Material UI — готовые компоненты, но меньше гибкости

## 3. Структура базы данных

### Таблица `game_sessions`
Хранит информацию об игровых сессиях.

| Поле | Тип | Описание |
|------|-----|----------|
| id | UUID | Уникальный идентификатор |
| wordList | text[] | Список слов для поиска |
| grid | text[][] | Игровое поле 10×10 |
| status | varchar | Статус: waiting/in_progress/finished |
| maxPlayers | integer | Максимум игроков (2-6) |
| duration | integer | Длительность в секундах |
| createdAt | timestamp | Время создания |
| endsAt | timestamp | Время окончания |

### Таблица `game_players`
Игроки в сессиях.

| Поле | Тип | Описание |
|------|-----|----------|
| id | UUID | Уникальный идентификатор |
| sessionId | UUID | Ссылка на сессию |
| name | text | Имя игрока |
| isBot | boolean | Является ли ботом |
| color | text | Цвет для отображения |
| turnOrder | integer | Порядок хода |
| firstWordTime | integer | Время первого слова (сек) |
| team | varchar | Команда (red/blue/green/yellow) |

### Таблица `found_words`
Найденные слова.

| Поле | Тип | Описание |
|------|-----|----------|
| id | UUID | Уникальный идентификатор |
| sessionId | UUID | Ссылка на сессию |
| playerId | UUID | Ссылка на игрока |
| word | text | Слово |
| startRow/col | integer | Начальные координаты |
| endRow/col | integer | Конечные координаты |
| direction | varchar | Направление |
| foundAt | timestamp | Время нахождения |

## 4. API Endpoints (tRPC)

### game.createSession
Создаёт новую игровую сессию с сгенерированным полем.

**Input:** `{ maxPlayers: number, duration: number }`
**Output:** `{ sessionId, grid, wordList, maxPlayers, duration }`

### game.joinSession
Присоединяет игрока к сессии.

**Input:** `{ sessionId: string, playerName: string }`
**Output:** `{ playerId, color, playersCount, isHost }`

### game.startGame
Запускает игру (только хост).

**Input:** `{ sessionId: string }`
**Output:** `{ message, grid, playerCount }`

### game.submitWord
Проверяет и регистрирует найденное слово.

**Input:** `{ sessionId, playerId, word, startRow, startCol, endRow, endCol, direction }`
**Output:** `{ success, error?, word?, playerScore?, results?, gameEnded? }`

### game.getSessionState
Возвращает текущее состояние игры.

**Input:** `{ sessionId: string, playerId?: string }`
**Output:** Полное состояние сессии с игроками, словами, результатами команд

### game.addBot
Добавляет бота в сессию.

**Input:** `{ sessionId: string, botName: string }`
**Output:** `{ playerId, color, playersCount }`

### game.setTeam
Устанавливает команду игрока.

**Input:** `{ sessionId: string, playerId: string, team: 'red' | 'blue' | 'green' | 'yellow' | null }`
**Output:** `{ success, team }`

## 5. Логика игры

### 5.1 Генерация поля
1. Выбирается случайный набор слов (15 штук)
2. Слова размещаются на поле 10×10 в случайных направлениях
3. Пустые клетки заполняются случайными буквами
4. Поле и список слов сохраняются в БД

### 5.2 Проверка слов
1. Проверка длины (минимум 3 буквы)
2. Проверка наличия в списке допустимых слов
3. Проверка направления (горизонтально/вертикально/диагонально)
4. Проверка совпадения букв на поле
5. Проверка, что слово ещё не найдено

### 5.3 Определение победителя
1. Сортировка по количеству найденных слов (убывание)
2. При равенстве — по времени первого найденного слова (возрастание)
3. В командном режиме — суммарный счёт команды

## 6. Real-time синхронизация

### 6.1 Polling (текущая реализация)
Клиент опрашивает сервер каждые 2 секунды для получения актуального состояния.

**Плюсы:** Простота реализации, работает через HTTP
**Минусы:** Задержка до 2 секунд, лишний трафик

### 6.2 WebSocket (подготовлено)
Реализован WebSocket сервер на порту 3001 для мгновенной доставки сообщений.

**Плюсы:** Мгновенная доставка, меньше нагрузки
**Минусы:** Требует отдельного порта, сложнее масштабировать

## 7. Бот

### 7.1 Алгоритм
1. Бот знает все слова на поле (имеет "идеальное зрение")
2. Выбирает слова в случайном порядке
3. Задержка перед нахождением настраивается (easy/medium/hard)
4. Может совершать ошибки с заданной вероятностью

### 7.2 Конфигурации
- **Easy:** 15 сек между словами, 30% ошибок
- **Medium:** 8 сек между словами, 15% ошибок
- **Hard:** 4 сек между словами, 5% ошибок

## 8. Командный режим

### 8.1 Механика
- Игроки делятся на команды (красная, синяя, зелёная, жёлтая)
- Счёт команды = сумма слов всех игроков команды
- Побеждает команда с наибольшим счётом

### 8.2 Реализация
- Поле `team` в таблице `game_players`
- Endpoint `setTeam` для выбора команды
- Расчёт результатов по командам в `getSessionState`
